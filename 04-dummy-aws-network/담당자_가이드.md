# AWS Network 담당자 가이드

모임 전에 **이미 동작하는 앱 앞단의 AWS 네트워크**를 직접 구성합니다.

Next.js/NestJS/Docker를 다시 만들지 마세요.
EC2에서 `curl localhost`가 되는 상태를 출발점으로 둡니다.

---

## 당신이 구성할 것

```text
VPC
Subnet (public 2개 이상 — ALB 요구사항)
Route Table
Internet Gateway
Security Group (ALB용 / EC2용 분리)
ALB
Target Group
Health Check
```

완료 모습:

```text
Internet
   ↓
ALB
   ↓
EC2 :80
   ↓
Docker Port Publish
   ↓
Nginx :80
   ↓
Docker Network
   ├─ frontend:3000
   └─ backend:4000
```

선택:

```text
Route53
ACM / HTTPS
RDS
```

---

## 작업 순서 체크리스트

1. [ ] 앱이 EC2에서 `curl localhost/health` 되는 것 확인
2. [ ] VPC 생성 (예: 10.0.0.0/16)
3. [ ] 퍼블릭 서브넷 2개 (서로 다른 AZ)
4. [ ] Internet Gateway 생성 후 VPC에 연결
5. [ ] 퍼블릭 라우트 테이블: `0.0.0.0/0 → IGW`
6. [ ] 서브넷을 그 라우트 테이블에 연결
7. [ ] SG-ALB: 인바운드 80 (0.0.0.0/0 또는 실습 범위)
8. [ ] SG-EC2: 인바운드 80의 **Source = SG-ALB**, SSH는 내 IP
9. [ ] EC2를 새 퍼블릭 서브넷으로 옮기거나, 처음부터 그 서브넷에 생성
10. [ ] Target Group (HTTP 80), 헬스체크 `/health`
11. [ ] ALB (internet-facing, 서브넷 2개), 리스너 80 → Target Group
12. [ ] 타깃에 EC2 등록, healthy 확인
13. [ ] 브라우저로 ALB DNS 접속
14. [ ] EC2 SG에서 인터넷 80 직접 접근을 닫아도 ALB로는 열리는지 확인

## 0. 출발점 확인

EC2에서:

```bash
cd ~/04-dummy-aws-network   # 또는 배포된 프로젝트 경로
docker compose ps
curl -i http://localhost/health
curl -i http://localhost/api/health
curl -i http://localhost/
```

이게 안 되면 네트워크를 붙이기 전에 배포 담당 가이드로 앱부터 살립니다.
비상 시 `backup/deploy-ready`를 사용합니다.

## 1. VPC / Subnet / IGW / Route Table

콘솔: **VPC → Your VPCs → Create VPC**

실습에 충분한 최소값:

```text
VPC CIDR: 10.0.0.0/16

Public subnet A: 10.0.1.0/24  (AZ-a)
Public subnet B: 10.0.2.0/24  (AZ-b)
```

Internet Gateway:

```text
Create IGW → Attach to VPC
```

Route Table (public):

```text
Destination: 0.0.0.0/0
Target:      igw-xxxx
```

두 퍼블릭 서브넷을 이 테이블에 연결합니다.
서브넷의 **Auto-assign public IPv4**를 켜야 SSH와 초기 테스트가 쉽습니다.

CLI로 한다면 예시는 아래와 같습니다. 콘솔로 해도 됩니다.

```bash
aws ec2 create-vpc --cidr-block 10.0.0.0/16 --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=studyboard-vpc}]'
```

이후 subnet / igw / route는 콘솔이 실수 적습니다. 실습 발표에서는 콘솔 클릭 경로를 설명해도 충분합니다.

## 2. Security Group 분리

**SG-ALB** (`studyboard-alb-sg`)

```text
Inbound
  80  TCP  0.0.0.0/0     (실습. 가능하면 팀 IP)
  443 TCP  0.0.0.0/0     (HTTPS를 붙일 때)
Outbound
  all
```

**SG-EC2** (`studyboard-ec2-sg`)

```text
Inbound
  22  TCP  내 IP
  80  TCP  SG-ALB만      ← 핵심. 인터넷 직접 80을 남기지 않기
Outbound
  all
```

EC2에 할당하는 그룹을 SG-EC2로 바꿉니다.
ALB에는 SG-ALB만 붙입니다.

변경 전에 SSH가 끊기지 않도록 22는 유지하세요.

---

## 3. Target Group

```text
Type: Instance
Protocol: HTTP
Port: 80
VPC: studyboard-vpc
Health check path: /health
Health check protocol: HTTP
Healthy threshold: 2
Interval: 15s
Success codes: 200
```

타깃 등록: EC2 인스턴스, 포트 80.

헬스체크가 실패하면:

```bash
# EC2에서
curl -i http://localhost/health
docker compose logs nginx
```

Nginx가 `/health`를 backend로 넘기는지 확인합니다. 이 더미는 이미 그렇게 되어 있습니다.

---

## 4. ALB

```text
Scheme: internet-facing
IP type: IPv4
VPC: studyboard-vpc
Subnets: public A, public B
Security group: SG-ALB
Listener: HTTP 80 → Forward to Target Group
```

생성 후 DNS 이름 예:

```text
studyboard-xxxx.ap-northeast-2.elb.amazonaws.com
```

확인:

```bash
curl -i http://studyboard-xxxx.ap-northeast-2.elb.amazonaws.com
curl -i http://studyboard-xxxx.ap-northeast-2.elb.amazonaws.com/health
curl -i http://studyboard-xxxx.ap-northeast-2.elb.amazonaws.com/api/health
```

브라우저로 같은 주소에 접속해 게시글이 보이는지 확인합니다.

타깃 상태가 **healthy**여야 합니다. `unhealthy`이면 ALB는 502를 줍니다.

---

## 5. 최종 검증 (직접 접속 차단)

EC2 SG에서 `0.0.0.0/0:80` 규칙을 제거합니다.
남은 80은 **SG-ALB → EC2** 뿐입니다.

```text
http://EC2_PUBLIC_IP     → 실패해야 정상
http://ALB_DNS           → 성공해야 정상
```

이게 되어야 “네트워크를 이해했다”고 볼 수 있습니다.

---

## 6. 선택 과제

시간이 있으면 아래를 추가합니다.

### HTTPS / ACM / Route53

```text
ACM에서 인증서 발급 (us-east-1이 아니라 ALB와 같은 리전)
ALB 리스너 443 추가, 80은 443 리다이렉트
Route53 A(Alias) → ALB
```

### RDS

```text
Private subnet 2개 추가
NAT Gateway (private가 아웃바운드 필요할 때)
RDS MySQL
EC2 SG → RDS SG 3306만 허용
backend DB_HOST를 RDS 엔드포인트로 변경
```

RDS는 비용과 시간이 더 듭니다. 핵심 발표는 ALB까지면 충분합니다.

## 자주 나오는 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| ALB 생성 안 됨 | 서브넷 1개만 선택 | AZ 2개 이상 |
| unhealthy | `/health` 404 | Nginx location /health |
| unhealthy | SG가 ALB를 거부 | EC2 80 소스 = SG-ALB |
| 타임아웃 | 퍼블릭 서브넷/IGW/라우트 누락 | 0.0.0.0/0 → IGW |
| 502 | 타깃 unhealthy 또는 nginx down | compose ps, curl localhost |
| SSH 끊김 | SG에서 22 삭제 | 22 내 IP 유지 |

---

## 발표 때 보여주면 좋은 화면

1. VPC 리소스 맵 (서브넷, IGW, 라우트)
2. SG 인바운드: ALB는 80, EC2 80은 ALB만
3. Target Group healthy
4. 브라우저 ALB DNS
5. EC2 Public IP 직접 접근 실패 vs ALB 성공

## 완료 기준

```text
Target Group: healthy
curl ALB_DNS           성공
curl ALB_DNS/api/health 성공
EC2 공인 IP 직접 80     실패 (SG로 막은 뒤)
```

모임 당일에는 더미 EC2가 아니라 **방금 배포된 실제 서비스 EC2**에 같은 네트워크를 붙입니다.
